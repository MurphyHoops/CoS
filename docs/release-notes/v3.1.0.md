# CoS 3.1.0

**Generic project runtime + durable provider transport suspension**

CoS 3.1 extends the standalone 3.x runtime in two directions: projects can now tell CoS how they verify completion without hard-coding a domain into the scheduler, and temporary provider/network loss is now a first-class suspension state rather than an executor failure.

## Project Runtime Profile

A project may add an optional `.cos/project.json`.

It can define:

- named direct-exec verification tasks;
- `task_success`, `path_exists` and `path_absent` completion predicates;
- `all` / `any` aggregation;
- explicit `auto_stop` for machine-verified completion.

Projects without a profile keep existing behavior.

Core adds one bounded `project_runtime` procedure with `status` and `check` actions. Status intentionally does not expose executable argv or the native project path.

Profile and predicate paths are resolved through the bound-project sandbox, including symlink
containment and use-time revalidation. Profile reads require read permission, path predicates
require metadata permission, and command predicates require command permission. Verifier output is
not echoed into model-facing completion status.

Automatic command-backed completion is durably claimed before the verifier starts. A crash or
executor rebind after that boundary does not replay an ambiguous verifier command.

## Provider Transport Suspension

The connection/tunnel authority now projects provider transport into:

- `ready`;
- `suspended` for offline/startup/reconnecting states;
- `blocked` for configuration/auth/disconnected states.

Provider transport is independent from executor health. During suspension CoS preserves durable mission debt and freezes provider-dependent failure budgets rather than escalating silence into Self-Healing failure.

On reconnect, one serialized reconciliation resumes the same durable commands, waits, Stop intent, Goal state, workers and recovery ownership.

### Long-Run

- Connectivity-dependent wait providers are not inspected while transport is suspended and do not spend monitor-error budget.
- Local process/timer waits can still resolve offline.
- A resolved local wait may become `owed`, but its provider continuation remains parked until connectivity returns.
- Active Long-Run work owns the next automatic provider transition, so Goal no longer races `session_wait` continuations.

### Self-Healing

- New recovery episodes do not start while provider transport is unavailable.
- Offline time does not consume executor-recovery budget.
- A 3.0-era `recovery_failed` episode is automatically recoverable only when the replacement send is still provably `not-attempted`.
- `dispatched-unresolved` and `sent` recovery checkpoints remain fail-closed and are never replayed by reconnect logic.

### Stop, workers and browser input

- A durable exact-turn Stop remains pending across an outage and resumes as the same command after reconnect.
- Worker/bootstrap/revival browser deadlines are suspended rather than failed by offline time.
- Accepted browser input no longer turns a long transient outage into a 65-second startup failure.
- Older queued startup failures are retried after reconnect using the same durable UUID; no duplicate authored input is enqueued.

## Compatibility

The app and extension version together as 3.1.0.

Bridge protocol remains **14** because this release does not introduce an incompatible app ↔ extension wire shape. Reload the matching companion extension after updating the app as usual.
